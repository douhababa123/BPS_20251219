# 能力评估网页编辑与季度历史设计

## 背景

当前“能力评估”页面只能查看能力现状、目标和 GAP，矩阵颜色还按 GAP 大小区分；后端现有新增/修改接口也没有完整的本人权限、`目标 >= 现状` 和逐次历史校验。业务需要在默认矩阵中直接维护能力数据，并保留每个季度内每一次修改的完整历史，同时主页面始终展示最新版本。

## 目标与非目标

目标：

- 管理员可编辑所有员工，普通工程师仅可编辑自己的能力评估。
- 现状和目标使用 `0–5` 整数下拉框；现状必填且 `0` 是有效能力值。
- 目标必须大于或等于现状；相等显示绿色，大于显示红色和 GAP 数值。
- 每次保存同时更新最新投影并追加一条不可覆盖的完整历史快照。
- 历史记录可按员工、技能、年份和季度通过 API 查询，并可取得季度最后版本。
- 将现有评估安全迁移为历史基线，不丢失旧年度记录。

本期不提供历史时间线页面，不开放卡片视图和普通表格视图编辑，也不引入审批、批量编辑、实时协作或复杂冲突合并。

## 已确认的方案

采用“当前表 + 独立历史表”：

- `competency_assessments` 作为每个员工、每项技能的最新投影，只保留一条当前记录。
- 新增 `competency_assessment_history`，每次修改追加完整快照，旧记录永不被业务保存操作覆盖。
- 能力画像、任务匹配、GAP 汇总等现有读取方继续读取当前表，避免把历史重复计入统计。

没有采用以下方案：

- 把现有表改成纯追加表并让所有读取方改查“最新记录”视图：影响面大，遗漏筛选会重复统计。
- 将历史存入 JSON 审计日志：难以可靠查询季度最终版本，也不便做字段约束。

## 数据模型

`competency_assessment_history` 保存：历史 ID、当前评估 ID、迁移前来源评估 ID、员工 ID、技能 ID、现状、目标、GAP、评估日期、年份、季度、备注、修改时间、修改用户和来源类型。

规则如下：

- `current_level`、`target_level` 均为整数 `0–5`。
- `target_level >= current_level`，GAP 固定为 `target_level - current_level`。
- 季度按服务端修改时间计算：1–3 月 Q1、4–6 月 Q2、7–9 月 Q3、10–12 月 Q4。
- 网页保存的历史记录必须带 `changed_by_user_id`；迁移基线允许为空，并标记 `MIGRATION_BASELINE`。
- 当前表唯一约束从“员工 + 技能 + 年份”调整为“员工 + 技能”。年份、评估日期仍记录最新保存发生的时间。

## 迁移与回滚

迁移在事务中按以下顺序执行：

1. 创建历史表、约束和查询索引。
2. 将全部现有评估复制为历史基线；年份和季度优先取原评估日期，缺失时依次回退到更新时间和迁移时间。
3. 若同一员工、同一技能有多个旧年度记录，历史表全部保留；当前表按 `assessment_date`、`updated_at`、`created_at` 和 ID 的稳定顺序保留最新一条。
4. 把历史基线关联到保留的当前记录，删除当前表中的旧重复投影。
5. 将现状/目标约束调整为 `0–5`，建立“员工 + 技能”唯一约束。
6. 校验历史基线数量等于迁移前记录数量、当前表无重复、等级和 GAP 约束均有效。

任何校验失败都回滚事务。Jetson 执行前必须具有数据库备份或可验证的恢复点；应用回滚时保留兼容的新历史表，数据库结构回退仅使用经过验证的恢复脚本或备份。

## API、事务与权限

新增统一保存接口：

`PUT /api/competency-assessments/employee/{employee_id}/skill/{skill_id}`

请求包含必填 `current_level`、`target_level` 和可选 `notes`。接口在同一数据库事务中完成：验证用户与目标员工、验证员工和技能存在、锁定/创建当前记录、更新最新投影、追加历史快照，然后返回最新评估。

- 管理员角色 `admin` 可修改所有员工。
- 普通用户通过 `users.email = employees.email` 解析本人，只允许目标 `employee_id` 等于本人员工 ID。
- 后端权限和数值校验是最终边界；前端的隐藏或禁用仅用于交互提示。
- 目标小于现状或等级越界返回 422，越权返回 403，员工/技能不存在返回 404。
- 任一步失败时事务整体回滚，不能出现当前数据已更新但历史缺失的状态。

新增 `GET /api/competency-assessments/matrix`，专门返回所有在职员工、所有有效技能、已有评估单元格和逐行 `can_edit`。这样即使员工或技能尚无评估，矩阵仍能显示“点击录入”，同时现有 `/full` 继续只返回真实评估，避免 Dashboard、能力画像和 GAP 统计把空单元格当成记录。`can_edit` 只是前端提示，不能替代保存接口的权限校验。另新增受权限保护的历史查询接口，可筛选员工、技能、年份、季度，并通过 `latest_per_quarter=true` 只返回每季度最后一条；普通用户只能查询本人，管理员可查询所有人。本期不在页面展示历史查询结果。

## 页面交互

编辑仅发生在“能力评估”的默认矩阵视图：

- 有权限的单元格可点击，并可通过 Enter/Space 打开编辑弹窗。
- 已有记录显示 `现状/目标`；没有记录的可编辑单元格显示“点击录入”。
- 无权限单元格保持只读；卡片视图和表格视图也保持只读。
- 弹窗固定显示员工与技能，提供现状、目标和可选备注。
- 现状是必填的 `0–5` 下拉框；选择现状前目标不可用。
- 目标下拉框只提供从现状到 5 的选项。若提高现状使旧目标失效，立即清空目标、显示错误并禁用保存。
- 保存期间禁止重复提交；成功后关闭弹窗并重新加载评估、矩阵和所有汇总数据；失败时保留用户输入并显示服务端错误。

显示规则统一为：

- `目标 = 现状`：绿色，不显示 GAP。
- `目标 > 现状`：红色并显示 `GAP N`。
- 不再根据 GAP 为 1、2 或更大使用黄色、深红等不同等级颜色。
- `0` 是有效数值，必须显示为 `0`，参与平均值和 GAP 计算；只有不存在评估记录时才显示未录入状态。

## 测试与验收

后端自动测试覆盖 `0–5`、`目标 >= 现状`、管理员/本人/越权、首次录入、重复修改、事务回滚、季度边界、季度最后版本和历史访问权限。迁移测试覆盖全部基线复制、跨年度重复记录去重、约束与幂等保护。

前端测试覆盖矩阵可编辑状态、键盘操作、弹窗联动、目标选项、错误保留、绿色/红色显示、GAP 文本、有效零值和保存后刷新。还要运行 TypeScript、针对性 ESLint、生产构建，并验证能力画像、Dashboard 和任务匹配没有因当前表去重或零值语义发生回归。

发布使用现有 GitHub Actions Jetson 流程。部署后分别使用管理员和普通工程师账号验证权限、编辑、颜色和 GAP，并通过只读查询核对一次保存同时产生一条最新投影和一条历史记录。

## 验收标准

1. 管理员能编辑任何员工，普通工程师只能编辑本人。
2. 现状必填且可为 0；现状和目标只能选择整数 0–5。
3. 目标小于现状在前端无法选择，绕过前端提交也返回 422。
4. 相等为绿色且不显示 GAP；目标更高为红色并显示准确 GAP，不再按 GAP 大小区分颜色。
5. 每次成功保存都更新当前表并新增且仅新增一条完整历史；失败不会产生部分更新。
6. 同一季度所有修改均保留，季度最后版本查询返回该季度最后一次修改。
7. 主页面显示全局最新版本，卡片和表格视图保持只读。
8. 所有旧数据进入历史基线，当前表每个员工和技能只有一条最新记录。
9. 自动化检查、迁移校验、Firefox 页面验收和 Jetson GitHub Actions 部署全部通过。
