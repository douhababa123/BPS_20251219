# 实现说明（2026-10-23）

## 能力现状与 GAP

现状、目标各自保持必填整数 0–4，允许现状高于目标。编辑界面不再因提高现状而清空目标。业务 GAP 逐技能计算 `max(目标 - 现状, 0)`，随后累加；例如两个技能分别为 4/2、1/3，总 GAP 为 0 + 2 = 2，不能相互抵消。达标和超额达标均为绿色。

当前评估、历史评估 API、评估矩阵、个人/团队汇总、季度趋势均采用非负业务 GAP。原始现状、目标及历史保持不变；数据库原有计算列可能保留有符号差值，但接口不直接暴露其负值作为业务 GAP。

年度总览沿用固定年初基线目标与同批技能的计算方式，其原有逐技能非负 GAP 规则通过回归验证。本次不改变年度基线导入规则，也不重构旧版 Excel 导入工具。

普通任务申请创建为 `pending_approval`，通知该 Site 审批人。每次更换工程师（包括同 Site、管理员改派、从已完成任务改派）重新进入待审批，并清除上一轮拒绝原因。未更换工程师的普通编辑不会额外重置审批。

只有本轮指定审批人可以通过/拒绝；Wang Ning 可以审批分配给自己的任务。全局管理员仍保留管理功能，但不能通过通用编辑接口绕过待审批状态。审批通过后为 `planned`，保留工程师接受任务的步骤。

自己首次登记并分配给自己的日程沿用免审批规则。用户已确认取消管理员“强制指派”免审批例外：前端移除该按钮和直接成功反馈，统一使用“提交申请”；旧 `/matching/force-assign` 地址保留管理员访问限制，但委托普通指派逻辑，创建待审批任务并通知指定 Site 审批人，旧页面也不能绕过审批。即使管理员通过任务分配给自己指派任务，也必须经过 Site 审批。

## 过期审批与并发保护

任务新增 `approval_version`。前端提交审批时发送当时看到的版本；后端锁定任务行，检查版本、状态、当前 Site 审批人。任务修改、改派、审批决定更新版本，通用编辑及执行状态更新用条件更新防止并发覆盖。旧审批页面返回 409，必须刷新。

日程、任务分配、管理端均使用后端 `can_approve` 判定按钮与待办。通知仅发送当前指定审批人，不再广播给全部管理员。
